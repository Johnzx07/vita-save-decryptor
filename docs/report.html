01The app in one minute

What it is, why it exists, and what makes this version different.

Vita Save Decryptor (native) turns a PS Vita CMA save backup (savedata.psvimg) into plain files ready for the Vita3K emulator. It is a single Windows executable — no install, no setup.

0
Online services needed
1
Runtime dependency (pycryptodome)
4/4
Encrypted files byte-exact vs reference
~10s
Typical decrypt time per save

The problem this solves

The original tooling for CMA backups required an external program (psvpfsparser.exe) that phoned home to the F00D key service at cma.henkaku.xyz. If that service goes down — or you're offline — decryption stops working. This project reverse-engineered the entire PFS encryption scheme and re-implemented it in pure Python, so keys are now derived locally from the save's own sealed key.

Bottom line Same output as the original tool — verified byte-for-byte — with zero network access and no bundled parser executable.

02How to use the app

From backup folder to decrypted save in four steps.
  1. Get your CMA backup + key
    On a PS Vita with the CMA plugin, back up the game's savedata. You'll get a folder containing savedata.psvimg — and the site shows you a 64-character hex key. Write it down; you need it for every backup.
  2. Launch VitaSaveDecryptor.exe
    Double-click the executable (from the GitHub release). No installation, no admin rights needed.
  3. Point it at your backup & enter the key
    Click Browse… and select either the .psvimg file itself or any folder that contains it. Paste the 64-hex CMA key into the field.
  4. Choose an output folder & hit Decrypt
    Pick where decrypted files should go, then click Decrypt Save…. Watch the six pipeline stages complete — your save is ready for Vita3K.
The main window — pick a backup, enter the CMA key, choose output, decrypt.
Good to know Your original backup is never modified. Everything is written to the separate output folder you chose. Re-running on the same backup always produces identical results (the process is fully deterministic).

03Output & troubleshooting

What you get, and what to do when something goes wrong.

What the output looks like

The decrypted set mirrors the game's PFS savedata layout:

your_output_folder/
├── system.dat            ← save data (encrypted → now plain)
├── sce_sys/
│   ├── param.sfo         ← metadata (title, size, version…)
│   ├── sdslot.dat        ← slot info
│   ├── safemem.dat       ← safe memory
│   ├── keystone          ← Henkaku keystone (if present)
│   └── sealedkey         ← the key material used for decryption

Load this folder into Vita3K as a save file and you're done.

Common problems

SymptomCause & fix
"Invalid CMA key"The key must be exactly 64 hex characters. Copy it fresh from the CMA site — no spaces, no quotes.
"CMA extraction failed (stage 1)"Wrong CMA key for this backup, or a corrupted .psvimg. Each backup has its own unique key.
"No PFS save set found"The archive isn't a Vita savedata. Make sure you backed up the game's savedata, not the whole app package.
"PFS decryption failed (stage 2)"The sealed key didn't match this save — usually means the backup and key are from different backups. Pair them correctly.
Nothing happens on launchWindows SmartScreen may block unsigned exes: click More info → Run anyway. Or check your antivirus quarantine.
Note The app is fully offline, but the CMA key itself comes from the henkaku.xyz CMA site when you create a backup. If you lose your key, you'll need to re-back up (or find it in your browser history) — there's no way around that; it's how CMA works.

Requirements

  • Windows 10 or 11, 64-bit
  • A PS Vita CMA save backup (savedata.psvimg) + its 64-hex key
  • No internet connection required at any point during decryption

04How it was done

The reverse-engineering story — from a dead-end dependency to a byte-exact pure-Python decryptor.

The goal: remove the online key service. That meant answering one question — how does psvpfsparser turn a sealed key into per-file decryption keys? The answer required pulling apart the reference tool's C++ source and rebuilding its math from scratch.

P1
reconnaissance
Map the pipeline & capture ground truth
Documented the two-stage flow (CMA unpack → PFS decrypt), captured a real h-encore release save (PCSG90096) as a regression fixture, and recorded the reference tool's exact output byte-for-byte — the target to beat.
P2
source analysis
Read the reference implementation (read-only)
Pulled psvpfstools' C++ sources locally and traced the call path: xts_dec → pfs_decrypt_icv → XTS-AES. Confirmed the cipher is XTS-AES-128 with two derived keys, 0x8000-byte sectors, IEEE-1619 perturbation that carries across all 512 sub-blocks per sector.
P3
key derivation
Crack the klicensee — the breakthrough
The per-file keys derive from a 16-byte "klicensee" value. Brute-forcing candidate derivations of the sealed key, one stood out: AES-CBC decrypting the first 16 bytes of the sealed-key blob with a fixed PSVita system key — producing exactly the value the F00D service had returned. All four encrypted files then matched byte-for-byte.
P4
classification
Which files decrypt, which copy?
Parsed the set's files.db (SCENGPFS v3) and found a clean rule in the type field: type & 0x4000 → copy verbatim, otherwise XTS-decrypt. Verified against every file in the fixture — no hardcoded file lists.

04The ICV Merkle oracle

The final piece — resolving which salt belongs to which file, with zero guessing.

Each encrypted file is keyed by a per-file salt (a 32-bit value stored as the name of its .icv record). The set contains several salts and no direct "file → salt" mapping — so how do you know which one to use? Heuristics (entropy, text-likeness) worked for most files but failed on small binaries like keystone, where three candidate salts all looked plausible.

The insight The stored 20-byte ICV in each record is a Merkle root computed over the file's ciphertext sectors — not the plaintext. That makes it an oracle: for every candidate salt, compute the expected root and compare. Exactly one matches per file. Deterministic, no guessing.

05Technical reference

The exact math, for anyone who wants to reproduce it.

Pipeline

savedata.psvimg
CMA archive + 64-hex key
→
Stage 1 · unpack
psvimg-extract.exe (bundled, MIT) → PFS set: files.db + icv.db + .icv pages
→
Stage 2 · native decrypt
pure Python — keys derived locally, XTS-AES-128, ICV Merkle salt oracle
→
Plain files
ready for Vita3K

Key derivation chain

# 1. klicensee — AES-CBC decrypt of the sealed-key blob's first block
klicensee = AES-CBC-Decrypt( sealedkey_blob[0:16], key=PSVITA_FIXED_KEY, iv=zeros )

# 2. per-file keys (ctr selects data key vs tweak key)
base0   = SHA1( klicensee )
saltin  = salt.to_bytes(4,"little") + ctr.to_bytes(4,"little")     # 8 bytes
key_ctr = SHA1( base0 || SHA1(saltin).digest() ).digest()[ :16 ]
dec_key, tweak_enc_key = key_ctr(ctr=1), key_ctr(ctr=2)

# 3. ICV secret (for the Merkle oracle)
secret  = SHA1( SHA1(klicensee) || SHA1( [0xA, salt]_LE8 ) )

XTS-AES-128 sector decryption

# per 0x8000-byte sector: seed once, perturb across all 512 sub-blocks
seed = AES-ECB( tweak_enc_key, u64_LE( 0x8000 * sector_index ) )
for each 16-byte block i in the sector (i = 0..511):
    tweak_i = IEEE-1619-perturb( seed, i )          # GF(2^128) × x, carry across blocks
    plain[i] = AES-ECB-Decrypt( dec_key, cipher[i] XOR tweak_i )

05The salt oracle & constants

How the right salt is found — and every magic number in one place.

ICV Merkle tree (salt oracle)

# leaf per sector: HMAC-SHA1 over the CIPHERTEXT sector
leaf_j = HMAC-SHA1( secret, ciphertext_sector_j )
# complete binary tree, BFS heap layout (1-based; children of i are 2i, 2i+1)
root   = merkle_fold( leaves )                      # left-inherits / right-advances
match  = ( root == stored_icv_root_in_.icv_record ) # exactly one salt matches per file
